## WhatsApp chat events

A [WhatsApp agent](/documentation/build-agents/agents/whatsapp-agents/create-an-agent) sends chat events instead of call events. You subscribe in the same [Event Subscription](/documentation/build-agents/customize-agent-behaviour/event-subscription) screen; only the event list and payload differ.

### Events

| Event | Label in the dashboard | Fires when |
|---|---|---|
| `chat_completed` | **Chat Completed** | The chat closes, before any analysis. |
| `platform_analysis_completed` | **Platform Analysis Done** | Platform analysis (summary, key points, action items) succeeds. |
| `client_analysis_completed` | **Advanced Analysis Complete** | Your [Advanced Analysis](/documentation/build-agents/customize-agent-behaviour/advanced-analysis) succeeds. |
| `all_processing_completed` | **All Processing Done** | Everything after the chat has finished. |

They arrive in that order. An analysis event is skipped when its analysis didn't succeed, but `all_processing_completed` still fires and carries the status.

`chat_completed` fires when the chat [closes](/documentation/build-agents/agents/whatsapp-agents/create-an-agent#when-a-chat-opens-and-closes), not after each message.

Call events (`call_started`, `call_ringing`, `call_ongoing`, `call_completed`, `recording_completed`) never fire for a chat and aren't offered on a WhatsApp agent. Subscribing to one through the API returns `400`: *Event type 'call_completed' is not available for a WhatsApp agent — it can only be produced by a voice call.* Likewise, `chat_completed` can't be added to a voice agent.

### Chat payload

Every chat event carries these base fields. None of them has `call_id` or `call_sid`; use `entity_type` to tell chat events from call events on a shared endpoint.

| Field | Type | Description |
|---|---|---|
| `event_type` | string | One of the four events above. |
| `entity_type` | string | Always `"chat"`. |
| `chat_id` | string | Ringg's chat ID, as shown in **Logs → WhatsApp**. |
| `channel` | string | `"whatsapp"`. |
| `agent_id`, `agent_name` | string | The agent that handled the chat. |
| `version_id`, `version_slug`, `version_description` | string | The [agent version](/documentation/build-agents/test-and-improve/drafts-and-versions) that handled it. |
| `workspace_id` | string | Your workspace. |
| `status` | string | Chat status, for example `completed`. |
| `from_number` | string | The customer's WhatsApp number in E.164, for example `+919876543210`. |
| `to_number` | string | Your business number's Meta phone number ID, not the phone number itself. |
| `custom_args_values` | object | Custom variables for the chat, including values set by pre-call tools. |
| `created_at` | string | When the chat started, ISO 8601. |
| `transcript` | array | Messages in order, each an object with one key, `user` or `bot`. Text only. |

Each event adds:

| Event | Extra fields |
|---|---|
| `chat_completed` | none beyond the base fields |
| `platform_analysis_completed` | `analysis_data`, `platform_analysis_status` |
| `client_analysis_completed` | `analysis_data`, `client_analysis_status` |
| `all_processing_completed` | `platform_analysis`, `platform_analysis_status`, `client_analysis`, `client_analysis_status`, `classification` |

### Common questions

<AccordionGroup>
  <Accordion title="Why did chat_completed arrive hours after the last message?">
    The chat closes only when the agent calls **End Chat** or the agent's idle timeout passes (3 hours by default). Lower **End the chat after no messages for** under **Chat → Settings** if you need the event sooner.
  </Accordion>
  <Accordion title="Can one endpoint receive both call and chat events?">
    Yes. Subscribe it on each agent and branch on `entity_type` ([payload](#chat-payload)). To read a chat while it is still open, use [Logs → WhatsApp](/documentation/monitor/logs#whatsapp-chats).
  </Accordion>
</AccordionGroup>
